# API conventions

- REST over JSON, prefix `/v1`. NestJS controllers with DTOs built from the Zod schemas in `packages/shared` (nestjs-zod) for body,
  params, query and response (also generates OpenAPI).
- Auth: short-lived JWT access token (15 min) + httpOnly refresh cookie for dashboard users.
  Staff PIN login switches the refresh session to another member in the same org (`POST /v1/auth/pin-login`,
  requires `X-Branch-Id`; revokes the prior session). Device pairing (`X-Staff-Session`) is deferred.
- Ordering cancel/void (step 9b): `POST .../orders/:id/status` and `POST .../items/:itemId/void` accept optional
  `approval: { membershipId, pin }` when the actor lacks `orders.cancel`. Wrong PIN → 401 `PIN_INVALID`; approver
  without permission → 403; missing approval → 403 `MANAGER_APPROVAL_REQUIRED`. Stale `expectedVersion` → 409
  `ORDER_VERSION_CONFLICT` before PIN is checked. Five failed PIN attempts lock the target membership for 5 minutes (`PIN_LOCKED`).
- `GET|PUT /v1/staff/:membershipId/permissions` — per-employee permission overrides `{ grant[], deny[] }` (GET also returns `rolePermissions` and `effective`); `org.manage` (Owner) only, owner memberships and `org.manage`/`billing.manage` keys are rejected. Table QR rotation needs `tables.rotate_qr`. Reopening a completed order (`POST .../orders/:id/status` with `{ to: 'ready', reopen: true, reason?, expectedVersion }`) needs `orders.reopen` (403), is only `completed -> ready` (else `ORDER_INVALID_TRANSITION`), and returns `422 ORDER_REOPEN_BILL_CLOSED` once the table bill is closed; it cannot be combined with `undo`.
- `GET /v1/branches/:branchId/pin-users` — staff with a PIN and access to that branch (`orders.read`).
- Request context resolved by middleware: `{ userId?, membershipId?, orgId, branchIds, deviceId?, permissions }`.
  Handlers never read org from body/params. Branch ids in the path are checked against `branchIds`.
- Each request runs DB work in a transaction that first sets `SET LOCAL app.org_id`.
- Errors: `{ "error": { "code": "ORDER_INVALID_TRANSITION", "message": "...", "details": {} } }`.
  400 validation, 401 unauthenticated, 403 no permission or plan feature, 404 not found (also for
  other tenants' resources), 409 conflict (version/state), 410 gone (e.g. `INVITE_EXPIRED`), 422 business rule (e.g. `ORDER_INVALID_TRANSITION`,
  `PAYMENT_METHOD_NOT_ACCEPTED` when card is disabled on the branch), 423 locked (e.g. `PIN_LOCKED`), 429 rate limit.
  Staff/settings codes include `STAFF_ALREADY_MEMBER`, `LAST_OWNER`, `INVITE_EXPIRED`, `MANAGER_APPROVAL_REQUIRED` (ordering, step 9b), `PIN_INVALID`, `PIN_LOCKED`.
  Billing entitlements: `PLAN_FEATURE_REQUIRED` and `PLAN_LIMIT_REACHED` (403, `details` include `feature` or `limit`, `max`, `planKey`). `GET /v1/me` includes an `entitlements` snapshot for nav gating.
  Billing API (`billing.manage`): `GET /v1/billing`, `POST /v1/billing/checkout`, `/change-plan`, `/portal`.
  Checkout/change conflicts: `BILLING_USE_CHANGE_PLAN` (live Paddle sub — use change-plan), `BILLING_NO_SUBSCRIPTION` (no live sub / no customer id for portal), same-plan `CONFLICT` (409), except change-plan to the current plan while a change is scheduled (e.g. a pending cancel) removes that scheduled change. Free plan checkout → 400. Paddle is called only after the DB transaction has finished.
  Paddle provider failures → 502 `BILLING_PROVIDER_ERROR` with `details.paddleErrorCode` (never log Authorization or full request bodies).
  Public webhook: `POST /v1/billing/webhooks/paddle` (raw body + `Paddle-Signature`; missing/invalid secret or signature → 401; no `billing_events` row). A signed payload that cannot be mapped is stored with `error = 'unmappable_payload'` when it has an `event_id`.
  Public contact form: `POST /v1/public/leads` (no auth; body `leadCreateBodySchema` in `@app/shared`; 201 `{ ok: true }`, 400 on validation, 429 over the limit; never cached). A filled honeypot field `website` gets the same 201 and stores nothing. The API sees only the site server's address (no `trust proxy`), so its 30/min limit is a site-wide safety net; the site's form action limits per visitor.
- Idempotent creates: header `Idempotency-Key`; for orders it equals `client_order_id`.
- Pagination is page-number based everywhere (no cursors, no `limit`/`offset`/`perPage` params). Always-paged lists, which never return every row: orders (`GET /v1/branches/:branchId/orders`), products, `GET /v1/admin/users` and `GET /v1/admin/audit`. `?page=` defaults to 1 and `?pageSize=` to 10 (max 100); response `{ items, page, pageSize, total }`. Schema `pagedListQuerySchema` in `@app/shared`. On orders, `hiddenOlderCount` is only sent on page 1.
- Page pagination (opt-in): `?page=&pageSize=` (`page` >= 1, `pageSize` 1-100, default 10 when only `page` is sent), response `{ items, page, pageSize, total }`. Supported on staff, memberships, categories, modifier groups, branches, devices, tables (`/v1/branches/:branchId/tables`), `GET /v1/admin/plans` and `GET /v1/admin/orgs`. With neither param the endpoint returns every row (`page: 1`, `pageSize: total`), so existing clients keep working. Schemas: `pageQuerySchema` / `pageMeta` / `slicePage` in `@app/shared`. Staff and devices are scoped per caller in memory, so their page is cut after scoping.
- Money in API = integer minor units + `currency` (always the base currency). When the restaurant has a display currency, responses also carry `display: { currency, rate, itemStep, totalStep }` (orders: frozen at creation; POS menu and public menu: current) and clients convert with `formatMoneyForDisplay` / `convertMinorToDisplay` from `@app/shared`. The daily report is the exception: its amounts arrive already converted. Org settings: `PATCH /v1/org/settings` takes `displayCurrency` (null = off), `exchangeRate`, `displayItemStep`, `displayTotalStep`; another currency without a rate is 400 `EXCHANGE_RATE_REQUIRED`. It also takes `menuTheme` (the whole public-menu look, `menuThemeSchema`; replaces the stored value, per organization); GET returns it (default look when none saved). `GET` also returns `menuLookAllowed` (false on plans without `menu.branding`, i.e. Free). Without it, `PATCH menuTheme` with anything but the default look, and the cover upload, fail with 403 `MENU_THEME_NOT_IN_PLAN` (saving the default look and removing the cover still work). The public menu serves the default look and no cover while the plan lacks the feature, so a plan change needs no manual purge (the Paddle webhook already purges). `brandColor` (`#rrggbb`) is stored as typed; clients derive the colours with `resolveThemeBrand` / `menuThemeVars` from `@app/shared` (3:1 against the preset background, darkened or lightened if needed; text on it 4.5:1). `GET` also returns `menuCoverUrls` (`{url480,url960}` or null). The cover photo has its own endpoints: `POST /v1/org/menu-cover` (multipart `file`, JPEG/PNG/WebP up to 5 MB, cropped to 4:5, old file deleted) and `DELETE /v1/org/menu-cover`, both `org.manage`. The public menu carries `org.coverUrls` (default null) and `org.theme` (new fields default, so cached menus still parse). A save that includes `menuTheme`, and a cover upload or removal, purges the org's public menu cache like a menu edit. Dates ISO 8601 UTC; `businessDate` as `YYYY-MM-DD`.
- Realtime: Socket.io namespace `/rt`, room `branch:{branchId}`; events `order.placed`,
  `order.updated`, `order.item_updated`, `menu.availability_changed`, `branch.settings_updated` (payload `{ branchId }` — POS invalidates menu cache), each `{ orderId, version, change, ... }` where applicable
  (`change` identifies what happened: `placed`, `status`, `items_added`, `item_voided`, `item_status`, `cancelled`, `payment`).
- Naming: routes kebab-case plural nouns (`/v1/branches/:branchId/orders`), JSON camelCase,
  DB snake_case.
